# Service contract (infra ↔ services)

What `infra/teleport/src/components/AccessServices.ts` deploys and what each service expects.

## Namespace `teleport-access`

| Deployment | Image | Containers | Port | Bot / role |
|---|---|---|---|---|
| `teleport-mcp` | `k8s-teleport/teleport-access` (`mcp --http :8080`) | tbot sidecar + service | 8080 (`/mcp`, `/healthz`, `/readyz`) | `teleport-mcp` / `svc-teleport-mcp` |
| `access-broker` | `k8s-teleport/teleport-access` (`broker`) | tbot sidecar + service | 8081 (`/v1/*`, `/healthz`, `/readyz`) | `access-broker` / `svc-access-broker` |
| `access-agent` (optional) | `k8s-teleport/access-agent` | service | 8082 (broker events, health; reachable only from the broker) + 8083 (chat webhooks, only with teams/gchat) | `access-agent` / `svc-access-agent` |
| `tbot-ci-harness` (kind only, `services.harness.enabled`) | tbot | tbot only, writes Secret `ci-harness-identity` | – | `ci-harness` / `svc-ci-harness` |

Every bot joins with the **kubernetes** join method; the `TeleportProvisionToken` allows exactly the pod's ServiceAccount
(`teleport-access:<bot>`). tbot writes a renewing identity to an in-memory `emptyDir` at
`/var/run/teleport/identity/identity`; the Go service reads it with `NewDynamicIdentityFileCreds` and reloads on change.

## Environment (Go services, `TA_*`)

| Variable | Meaning |
|---|---|
| `TA_TELEPORT_ADDR` | auth service address (`teleport-cluster-auth.teleport.svc.cluster.local:3025`) |
| `TA_TELEPORT_IDENTITY_FILE` | identity file written by tbot |
| `TA_TELEPORT_INSECURE` | `true` only on kind |
| `TA_TELEPORT_EDITION` | `community` \| `enterprise` |
| `TA_MCP_SHARED_TOKEN` | bearer token the agent presents to `/mcp` (≥ 32 chars) |
| `TA_IDENTITY_SIGNING_KEY` | HMAC key (≥ 32 chars) that verifies the agent's per-turn `X-Teleport-Assertion`; the agent holds the same key as `IDENTITY_SIGNING_KEY` |
| `TA_MCP_POLICY_FILE` / `TA_BROKER_POLICY_FILE` | `/etc/teleport-access/policy.yaml` (ConfigMap `broker-policy`, rendered from the role catalog) |
| `TA_BROKER_API_TOKEN` | bearer token for the broker API |
| `TA_BROKER_WEBHOOK_SECRET` | HMAC secret for broker → agent events |
| `TA_BROKER_AGENT_WEBHOOK_URL` | `http://access-agent.teleport-access.svc.cluster.local:8082/v1/broker/events` (empty = no notifications) |
| `TA_BROKER_APPROVALS` | `setstate` (Community) \| `review` (Enterprise) \| `native` (disabled) |
| `TA_BROKER_MODE` | `watch` (default) \| `poll` |

Shared secrets live in Secret `access-services` (generated by Pulumi with `@pulumi/random`); read them with
`pulumi stack output mcpSharedToken --show-secrets`.

## MCP identity binding

The agent opens **one MCP session per chat principal** and sends, on every HTTP request, `Authorization: Bearer <shared>`
plus a fresh `X-Teleport-Assertion`: `b64url(payload).b64url(HMAC-SHA256(key, b64url(payload)))` with payload
`{sub, email, platform, platform_user_id, aud: "mcp", iat, exp (≤ iat+60), jti (UUID, single-use)}`. The server verifies
the signature, audience, lifetime and replay, binds the `sub` to the `Mcp-Session-Id` on first sight (a different `sub`
on that session is a 403) and ignores any `X-Teleport-User*` header. No tool accepts an identity argument (the agent
refuses any tool schema that does). The broker's `POST /v1/requests/{id}/approve|deny` uses the same assertion with
`aud: "broker"`: the approver is taken from the assertion, the body is `{reason}` only, and the broker independently
checks the approver's Teleport roles and rejects self-approval (username and email traits, case-insensitive). On stdio (Claude Code / Desktop) the principal is the local
operator (`TA_MCP_STDIO_USER` or the connected identity).

## Agent environment (TypeScript)

See `services/access-agent/src/config/schema.ts`. Chat credentials are mounted as 0400 files (one Secret per group:
`access-agent-llm`, `access-agent-slack`, `access-agent-teams`, `access-agent-gchat`) and referenced through `<NAME>_FILE`
environment variables, filled from the Pulumi secret object `teleport:chat` (`anthropicApiKey` or `claudeCodeOauthToken`,
`slackBotToken`, `slackAppToken`, `teamsAppId`, `teamsAppPassword`, `teamsTenantId`, `gchatProjectNumber`,
`gchatServiceAccountJson`). Slack runs in socket mode only, so there is no signing secret.
