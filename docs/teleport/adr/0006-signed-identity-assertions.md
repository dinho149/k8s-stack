# ADR 0006: Signed per-turn identity assertions between agent, MCP server and broker

Date: 2026-09-17. Status: accepted.

## Context

The chat agent creates access requests on behalf of a chat user through the MCP server and relays approve/deny clicks
to the broker. Both services originally authenticated the agent with a static shared bearer token and then trusted a
plaintext header (`X-Teleport-User`) or a JSON body field (`approver`) for *who* was acting. Anyone holding a token,
or any pod that could reach the ports (there were no NetworkPolicies), could therefore act as any Teleport user and
approve any request as any approver.

Options considered: keep bearer tokens and add NetworkPolicies only; mint short-lived signed assertions per turn;
full mTLS with SPIFFE workload identities issued by tbot.

## Decision

Signed assertions plus default-deny NetworkPolicies, on top of the bearer tokens.

- The agent mints an HMAC-SHA256 assertion for every HTTP request it makes: header `X-Teleport-Assertion`,
  `b64url(payload).b64url(HMAC(key, b64url(payload)))`, payload `{sub, email, platform, platform_user_id, aud, iat,
  exp, jti}`, lifetime at most 60 s, `jti` a single-use UUID, `aud` bound to the receiver (`mcp` or `broker`).
- The MCP server verifies signature, audience, lifetime and replay, binds the `sub` to the MCP session on first sight,
  and never reads `X-Teleport-User*`.
- The broker takes the approver identity only from the assertion; the approve/deny body is `{reason}`.
- The key (`TA_IDENTITY_SIGNING_KEY` / `IDENTITY_SIGNING_KEY`, at least 32 bytes) is generated by Pulumi and mounted
  as a file; the services refuse to start without it.
- NetworkPolicies allow MCP and broker ingress only from the agent pod, and the agent's internal port only from the
  broker.

## Consequences

- A leaked bearer token is no longer sufficient to impersonate a user or forge an approval; an attacker also needs
  the signing key, and possession of both still only works from a pod the NetworkPolicy admits.
- The Claude Code (subscription) backend cannot set dynamic headers, so the agent runs a per-turn loopback proxy that
  swaps in fresh assertions.
- The Go and TypeScript implementations are pinned to each other by a shared test vector
  (`services/teleport-access/internal/assertion/crosscheck_test.go`).
- mTLS via tbot workload identity remains a possible later hardening step and would compose with this design.
